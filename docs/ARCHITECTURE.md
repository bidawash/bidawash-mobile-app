# Architecture

How this repo is laid out, where the iOS and Android code lives, what's
shared, and what gets generated at build time. Read this if you're new to
the codebase or new to Expo.

For the roadmap, see [PROJECT-PLAN.md](./PROJECT-PLAN.md).
For store submission, see [STORE-SUBMISSION.md](./STORE-SUBMISSION.md).

---

## Overview

BidaWash is a single TypeScript/React Native codebase that compiles to a
native iOS app (`.ipa`) and a native Android app (`.aab` / `.apk`). It uses
the **Expo managed workflow**, which means there is no `ios/` or `android/`
folder in this repo — those native projects are **generated on demand by
EAS Build** from the JS code and `app.config.ts`.

```
┌────────────────────────────────────────────────────────────┐
│  TypeScript / React Native code  (src/, App.tsx)            │  ← what we write
├────────────────────────────────────────────────────────────┤
│  Expo SDK + config plugins  (app.config.ts)                 │  ← declarative config
├────────────────────────────────────────────────────────────┤
│  Native iOS project    │   Native Android project           │  ← generated by EAS
│  (Xcode, Swift/ObjC)   │   (Gradle, Kotlin/Java)            │     not in this repo
├────────────────────────────────────────────────────────────┤
│  TestFlight .ipa       │   Play Console .aab                │  ← produced by EAS Build
└────────────────────────────────────────────────────────────┘
```

## Where the iOS and Android code lives

Short version: **there is none in this repo (by design).**

The Expo managed workflow generates the native iOS and Android projects
from the JS code and `app.config.ts` whenever a build happens. EAS Build
runs this on Expo's cloud machines — that's why you don't need a Mac to
ship an iOS build.

If you ever need to inspect or modify the native projects directly, run:

```bash
npx expo prebuild
```

This creates `ios/` and `android/` folders. They're git-ignored
intentionally (see [.gitignore](../.gitignore)); committing them means
opting out of the managed workflow, which we do **not** do today. Anything
we need from the native layer (permissions, entitlements, custom URL
schemes, plugin code) is reachable through `app.config.ts` and Expo config
plugins.

## What's shared vs platform-specific

### Shared (>95% of the codebase)

Everything in `src/` and `App.tsx` runs unchanged on both platforms. React
Native maps JSX components like `<View>`, `<Text>`, `<Pressable>` to native
`UIView` (iOS) and `android.view.View` (Android) at runtime. Business
logic, navigation, state, theming, API calls — all shared.

### Platform-specific (when unavoidable)

Three escape hatches, in order of preference:

1. **`Platform.OS` checks in code** — small differences inline:

   ```ts
   import { Platform, StyleSheet } from 'react-native';

   const styles = StyleSheet.create({
     card: Platform.OS === 'ios'
       ? { shadowColor: '#000', shadowOpacity: 0.1 }
       : { elevation: 4 },
   });
   ```

2. **Platform file extensions** — Metro resolves `MyComponent.ios.tsx` for
   iOS builds and `MyComponent.android.tsx` for Android, falling back to
   `MyComponent.tsx`. Use this when a whole component needs to differ.

3. **Config plugins in `app.config.ts`** — modify the underlying native
   projects without leaving the managed workflow. We use this today for the
   Sentry plugin. Future examples might include APNs entitlements or custom
   Android intent filters.

### Assets

`assets/` is shared, but icons differ:

- `icon.png` — iOS app icon (Apple applies its own mask).
- `adaptive-icon.png` — Android adaptive-icon foreground (background color
  set in `app.config.ts`).
- `splash.png` — splash screen for both.
- `favicon.png` — web only.

## Configuration layers

There are three, each with a clear job:

| File              | Job                                                                     | Read at      |
|-------------------|-------------------------------------------------------------------------|--------------|
| `app.config.ts`   | Defines the app to Expo and to the generated native projects: bundle IDs, permissions (Info.plist / AndroidManifest entries), splash, icons, config plugins. Surfaces env vars to runtime via `extra`. | Build time   |
| `eas.json`        | Defines build profiles (`development` / `preview` / `production`) and submit destinations (App Store Connect, Play Console). Tells EAS Build whether to ship a simulator IPA or a signed App Store IPA. | Build time   |
| `.env`            | Local secrets only. Read inside `app.config.ts` at build time and surfaced into the JS bundle via `expo-constants`. Runtime code must pull from [src/lib/env.ts](../src/lib/env.ts) — the only typed accessor. | Build time   |

## What happens during an EAS Build

When you (or CI) run `eas build --profile preview --platform ios`, on
Expo's cloud machines:

1. EAS clones the repo at the chosen git ref.
2. Runs `npm install`.
3. Runs `npx expo prebuild` to generate `ios/` (or `android/`) from
   `app.config.ts`.
4. Compiles natively — Xcode for iOS, Gradle for Android.
5. Signs the binary with EAS-managed credentials (we never touch
   `.p12` / `.mobileprovision` locally).
6. Uploads the artifact and returns a download link.
7. If you ran `eas submit`, pushes it to TestFlight or Play Console.

For small JS-only changes (no native dep changes, no permission changes),
**EAS Update** can ship the new JS bundle over-the-air without rebuilding
the native binary — users get it on next app launch.

## Data flow (target architecture)

```
  Screen (src/features/X/)
        ↓ calls
  React hook (feature-local or src/hooks/)
        ↓ calls
  API module (src/api/)
        ↓ uses
  Supabase JS client  ──→  Postgres (Row Level Security enforces access)
                      ──→  Edge Functions (Phase 3 payments)
```

- **Phase 2** wires Auth + the read side: screens call hooks → api →
  Supabase with the user's JWT; RLS policies enforce what each user can
  read/write.
- **Phase 3** adds Edge Functions for payment creation, so secret keys
  (Stripe / Maya / GCash) never enter the app bundle.

## What lives outside the repo (and where)

| Concern                          | Lives in                                                  |
|----------------------------------|-----------------------------------------------------------|
| Native iOS Xcode project         | EAS Build cloud (regenerated each build)                  |
| Native Android Gradle project    | EAS Build cloud (regenerated each build)                  |
| iOS signing certs + provisioning | EAS-managed; no `.p12` / `.mobileprovision` files locally |
| Android upload key               | Managed by Google Play app signing                        |
| Push notification credentials    | APNs key in App Store Connect; FCM key in Play Console    |
| App Store / Play Store metadata  | App Store Connect + Play Console web UIs                  |
| Supabase schema (live)           | Hosted Postgres at supabase.com; mirror in `supabase/migrations/` (Phase 2+) |
| Privacy policy + terms HTML      | Hosted separately (Vercel / GitHub Pages, TBD)            |
| Crash reports / errors           | sentry.io                                                 |

## When we might "eject" / commit native projects

If we ever need a native module that Expo doesn't expose and that has no
config plugin, the path is:

1. Run `npx expo prebuild`.
2. Commit the generated `ios/` and `android/` folders.
3. Add the custom native code.
4. From then on, builds still work via EAS, but `app.config.ts` no longer
   re-generates those folders on each build — they become source of truth
   and must be hand-maintained.

This is effectively a one-way door, so we'd weigh it carefully. We have no
current need: push, QR scanning, camera, secure storage, payments, deep
links, and maps all have Expo-supported equivalents.
